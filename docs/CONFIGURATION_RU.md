# FreeRDPTun 0.1.3: полный справочник настроек

Конфигурация задаётся JSON-файлом. Настройки транспорта и статистики определяет
сервер; клиент получает эффективный профиль после UUID-авторизации, с проверкой
HMAC. Существующие UUID, сертификат, pin и адреса 10.77.0.0/24 сохраняются.

## Что именно настраивается

Снаружи остаётся настоящий FreeRDP: X.224, TLS, MCS, capabilities, activation,
DRDYNVC и канал `FreeRDPTun::IP::1`. Новые модификаторы работают с нашим
прикладным потоком внутри DVC: padding, дробление IP-пакета на фрагменты,
задержки отправки и token bucket. Нативный `rdpt-bridge` не изменён.

Размер прикладного фрейма не равен размеру TCP-сегмента, TLS record или
RDP graphics update. TCP не сохраняет границы записей приложения
([RFC 9293, раздел 3.7](https://www.rfc-editor.org/rfc/rfc9293)).
Использование FreeRDP и padding не гарантирует сходства с Windows-видеосессией:
TLS не скрывает время и длины передачи
([RFC 8446, E.3](https://www.rfc-editor.org/rfc/rfc8446#appendix-E.3)).

Автоматической калибровки по pcap, генерации рабочего стола/видеоприкрытия,
подмены TLS fingerprint, группирования нескольких IP-пакетов в один контейнер
или планировщика «всплеск/пауза» в 0.1.3 нет. `burst_bytes` является ёмкостью
token bucket, а не размером воспроизводимого RDP-всплеска.

## Загрузка, типы и значения по умолчанию

- **Формат:** один JSON-объект, без комментариев и завершающих запятых.
  Неизвестные поля и данные после объекта отклоняются. Загрузчик читает
  ограниченный объём до 1 MiB; держите конфигурацию существенно меньше.
- **Изменения:** горячей перезагрузки нет. Выполните `check`, перезапустите
  сервер, затем переподключите клиентов. Изменение серверного профиля применяется
  к новым сеансам, а не пересогласовывается в уже установленном канале.
- **Пути:** явно указанные относительные `certificate`, `private_key` и `bridge`
  разрешаются относительно каталога JSON, не текущего рабочего каталога.
  Пустой `bridge` означает файл рядом с исполняемой Go-программой.
- **Числа:** целые, не строки и не дроби. Все скорости в бит/с, размеры в байтах,
  секунды и миллисекунды указаны в именах. `100000000` = 100 Мбит/с;
  65536 байт = 64 KiB.
- **Пропуск поля:** в таблицах ниже «по умолчанию» означает значение загрузчика
  или эффективной политики. Шаблон `init-server` иногда явно задаёт другое
  значение, что отмечено отдельно.
- **Нули:** не имеют единого смысла. Для скоростей это отсутствие конкретного
  лимита, для `stats_interval_seconds` это только итоговый отчёт, для jitter
  это отсутствие задержки, для некоторых размеров/таймаутов это значение
  по умолчанию. Отрицательные значения отклоняются.
  Для переключателей используйте явные `true`/`false`, а не `null`.
- **Секреты:** UUID является секретом доступа. Не публикуйте серверный JSON,
  клиентский JSON и `server.key`; используйте права 0600 и защищённую передачу.

Команды ниже предназначены для вашей песочницы. Они не выполнялись при
подготовке 0.1.3:

```bash
/opt/freerdptun/freerdptun check -config /etc/freerdptun/server.json
```

```powershell
.\freerdptun.exe check -config .\client.json
```

`check` проверяет структуру и значения JSON. Он не открывает TUN, не подключается
к серверу и не подтверждает доступность native-библиотек, валидность файлов
сертификата или работоспособность маршрутизации.

## Общие поля верхнего уровня

| Поле | Где | Значение по умолчанию | Допустимые значения и назначение |
|---|---|---|---|
| `mode` | обе стороны | нет | `"server"` или `"client"`. Сервер поддерживается только на Linux. |
| `address` | обе стороны | нет | Сервер: адрес прослушивания, например `"0.0.0.0:3389"`. Клиент: `"host.example:3389"`. Обязателен числовой TCP-порт 1..65535; стандартный для эксперимента 3389. |
| `tun` | обе стороны | нет | Имя создаваемого интерфейса, обычно `"frdptun0"`. 1..15 байт; запрещены пробел, `/`, `\` и NUL. Чужой Linux-интерфейс с таким именем не захватывается. |
| `cidr` | обе стороны | нет | IPv4 адрес узла с префиксом, например `"10.77.0.1/24"` у сервера и `"10.77.0.2/24"` у клиента. Это не адрес сети `"10.77.0.0/24"`. |
| `mtu` | обе стороны | 1400; также при `0` | 576..9000. Должен совпадать у сервера и клиента; задаётся интерфейсу при автонастройке. Padding не увеличивает допустимый IP-пакет сверх MTU. |
| `bridge` | обе стороны | рядом с Go-программой | Путь к `rdpt-bridge` на Linux или `rdpt-bridge.exe` на Windows. Не путать с главным `freerdptun`. |
| `auto_configure_tun` | обе стороны | `true`, если поле отсутствует | `true`: назначить адрес и MTU своему новому интерфейсу; на Linux включить link, на Windows дождаться IPv4 `Preferred`. `false`: только создать интерфейс, дальнейшая настройка ваша. |
| `total_upload_bps` | обе стороны, смысл различается | 0 | 0..1000000000000. На сервере общий лимит client → server для всех сеансов. На клиенте дополнительный локальный предел upload этого клиента. |
| `total_download_bps` | обе стороны, смысл различается | 0 | Тот же диапазон. На сервере общий лимит server → clients. На клиенте дополнительный локальный предел download. |
| `handshake_timeout_seconds` | обе стороны | 20; также при `0` | 3..120. Собственный срок установления RDP/TLS/DVC и UUID-авторизации на соответствующей стороне. Отказная NLA-ветка имеет отдельный таймаут. |
| `idle_timeout_seconds` | обе стороны, с оговоркой | 60; также при `0` | 15..3600. Срок без принятого полного прикладного IP-сообщения или ping/pong. В сеансе v2 серверное значение применяется на обеих сторонах; клиентское проверяется при загрузке, но не переопределяет полученную политику. |
| `queue_packets` | обе стороны | 256; также при `0` | 16..4096. Очередь исходящих сообщений одного сеанса. На сервере новые IP-пакеты при переполнении отбрасываются; на клиенте применяется обратное давление на чтение TUN. Большая очередь не увеличивает пропускную способность и может увеличить задержку. |

`init-server` задаёт серверу оба глобальных лимита по 100000000 бит/с.
Отсутствие этих полей в написанном вручную JSON означает 0, не 100 Мбит/с.
На клиенте сгенерированные локальные лимиты равны 0.

Назначение IP создаёт штатный маршрут подключенной подсети в ОС. Программа
не меняет default route, DNS, NAT, forwarding и firewall. Ранее добавленные
ручные маршруты на других интерфейсах автоматически не удаляются.

## Поля только сервера

| Поле | Значение по умолчанию | Назначение |
|---|---|---|
| `certificate` | нет | Обязательный путь к серверному PEM-сертификату. Сохраняйте текущий файл при обновлении. |
| `private_key` | нет | Обязательный путь к PEM private key этого сертификата. Никогда не копируйте клиенту. |
| `clients` | нет | Непустой allowlist объектов, описанных ниже. |
| `max_connections` | 32; также при `0` | 1..256. Общий предел принятых серверных соединений, включая рукопожатия и NLA-отказы. Это не только число успешно авторизованных VPN-клиентов. |
| `rdp_decoy` | включён, 10 секунд, 16 сеансов | Объект раннего NLA-отказа, см. ниже. |
| `transport` | эффективный `baseline` с включёнными лимитами | Серверный объект модификации транспорта. Передаётся клиенту с HMAC. |
| `stats_interval_seconds` | 10 | 0..3600. Период `STATS` на обеих сторонах нового сеанса. `0`: без периодических записей, но с итоговой. |

Явно указанный объект `transport`, в том числе `{}`, или числовое
`stats_interval_seconds`, даже `0`, требует клиента 0.1.3+. JSON `null`
для этих полей загружается как отсутствие; использовать его как переключатель
совместимости не рекомендуется.

### Allowlist `clients[]`

| Поле | Значение по умолчанию | Допустимые значения и смысл |
|---|---|---|
| `id` | нет | Непустая уникальная метка для журнала, например `"test-01"`. Не секрет авторизации. |
| `uuid` | нет | Секрет в канонической форме 8-4-4-4-12 hex, ненулевой, уникальный. Рекомендуется результат `freerdptun new-uuid`; генерируется UUIDv4. |
| `ipv4` | нет | Уникальный IPv4 внутри серверного CIDR, не адрес сервера, сети или broadcast. Например `"10.77.0.2"`. |
| `upload_bps` | 0 | 0..1000000000000. Дополнительный предел client → server для этого UUID. |
| `download_bps` | 0 | Тот же диапазон. Дополнительный предел server → client для этого UUID. |

Глобальные и индивидуальные лимиты действуют одновременно; 0 снимает только
свой предел, но не другие. Общий серверный bucket разделяется между сеансами;
справедливое распределение скорости и гарантированная доля каждому клиенту
не реализованы. Разрешён один активный сеанс на UUID; второй не вытесняет первый.

Изменение `clients[]` требует перезапуска. Передавайте клиенту только его
секрет и параметры, не весь серверный allowlist.

### Объект `rdp_decoy`

| Поле | Если объект отсутствует | Если объект присутствует | Назначение |
|---|---|---|---|
| `enabled` | `true` | `false`, если пропущено | Включает отдельную раннюю отказную NLA-ветку. Указывайте явно. |
| `handshake_timeout_seconds` | 10 | 10 при пропуске/0 | 3..120 секунд на отказное соединение. |
| `max_connections` | 16 | 16 при пропуске/0 | 1..256 одновременно; также действует верхний `max_connections`. |

Фактический срок отказной ветки не превышает ни её собственного таймаута,
ни общего серверного `handshake_timeout_seconds`, отсчитываемых от accept.

Таким образом, отсутствие всего блока и `"rdp_decoy": {}` имеют разный смысл:
первое включает отказную ветку, второе выключает её. Для ясного отключения
используйте `{"enabled": false}`.

Клиент, предлагающий HYBRID/HYBRID_EX, получает X.224 Connection Confirm,
TLS и ранний CredSSP/TSRequest `STATUS_LOGON_FAILURE`, после чего соединение
закрывается. Обычный `mstsc` может показать свой запрос логина/пароля;
вид интерфейса зависит от клиента и его политик. Это не полноценный Windows
logon, NTLM/Kerberos или рабочий стол; NTLM challenge не выдаётся и до
делегирования пароля обмен не доходит.

Отбор основан на предложенных протоколах, а не имени приложения.
TLS-only `mstsc` в эту ветку не попадает; наш TLS-only FreeRDP-клиент идёт
в нативный `rdpt-bridge`. Отключение decoy не отключает рабочий DVC-туннель.
Объекта `rdp_decoy.hostname` в этом проекте нет: используется текущий
серверный сертификат, а не отдельная «Windows-машина».

## Поля только клиента

| Поле | Значение по умолчанию | Назначение |
|---|---|---|
| `uuid` | нет | Тот же секрет, что в соответствующей записи `clients[]` сервера. |
| `ipv4` | нет | Точный разрешённый сервером адрес; должен совпадать с адресом узла в клиентском `cidr`. |
| `server_sha256` | нет | Ровно 64 hex-символа SHA-256 DER leaf-сертификата сервера, без двоеточий. Проверяется pin и срок действия; режима accept-any нет. |

Клиентских сертификатов нет. Не добавляйте клиенту `transport`,
`stats_interval_seconds`, `rdp_decoy` или непустой `clients`: валидатор
отклоняет серверные настройки. `certificate`/`private_key` в клиентском режиме
не используются; клиенту эти поля и сами файлы не нужны.

`max_connections` проверяется как общее поле структуры, но в клиентском
режиме не создаёт несколько соединений. Клиент устанавливает один сеанс,
не переподключается автоматически и не создаёт несколько TUN.

## Серверный объект `transport`

Профили общие для всех UUID на сервере. Индивидуально через `clients[]`
задаются только адреса, секреты и лимиты; отдельных profile overrides
для одного клиента в 0.1.3 нет.

| Поле | По умолчанию | Допустимые значения и смысл |
|---|---|---|
| `mode` | `"baseline"`; также при пустой строке | `"baseline"` или `"profiled"`. Подробности ниже. |
| `rate_limit_enabled` | `true`, если пропущено | Независимый выключатель всех встроенных rate limiters нового сеанса, включая дополнительные локальные клиентские лимиты. `false` не выключает padding/jitter. |
| `rate_accounting` | `"ip"`; также при пустой строке | `"ip"`: считать полные внутренние IP-пакеты, включая IP-заголовки. `"frame"`: считать собственные DATA-фреймы, включая padding и наши заголовки. Это не лимит внешнего TCP/TLS/RDP на проводе. |
| `burst_bytes` | 65536; также при `0` | 16384..4194304. Ёмкость каждого token bucket. Начальный bucket полный; при простое запас восстанавливается, выше ёмкости не растёт. |
| `keepalive_min_seconds` | 10; также при `0` | 3..30. Нижняя граница интервала простоя исходящей передачи перед ping. |
| `keepalive_max_seconds` | равен эффективному min при пропуске/0 | От min до 30, строго меньше серверного `idle_timeout_seconds`. Выбирается целое число секунд равномерно, включая границы. |
| `reassembly_timeout_seconds` | 30; также при `0` | 1..120. Допустимый возраст незавершённой сборки IP-пакета из envelope-фрагментов. |
| `upload` | профиль без модификаторов | Объект для client → server; значения ниже. |
| `download` | профиль без модификаторов | Объект для server → client; значения ниже. |

### Режимы и ограничения скорости

- **`baseline`:** padding, fragmentation и jitter принудительно выключены
  в эффективной политике, даже если включены в исходном JSON. Сам JSON
  всё равно валидируется: неверный диапазон размеров не игнорируется.
- **`profiled`:** действуют явно заданные модификаторы каждого направления.
  Если все они выключены, DATA идёт в обычном формате без envelope.
- **Независимость лимитов:** `baseline` НЕ означает unlimited. Например,
  при `rate_limit_enabled: true` и глобальных лимитах 100 Мбит/с они
  сохраняются и в `baseline`. Для чистого замера без нашего шейпера
  явно задайте `rate_limit_enabled: false`.
- **Два уровня:** сервер применяет индивидуальный и общий bucket. Клиент
  дополнительно ограничивает направление минимумом ненулевых переданных
  сервером лимитов и своего локального `total_*_bps`. Нулевые значения
  в расчёте минимума не участвуют; все нули означают отсутствие ограничения.
- **Единицы учёта:** `ip` даёт более удобное сравнение полезного IP-трафика,
  но при padding внешний поток будет больше. `frame` включает собственные
  накладные расходы и padding, но всё равно не включает TLS/RDP/TCP/IP
  внешнего соединения.
- **Короткие всплески:** token bucket разрешает начальный/накопленный burst,
  поэтому мгновенная скорость может превысить установленную. Это не обещание
  строгого потолка на любом коротком временном окне.

Ping/pong не тарифицируются DATA-лимитером и не получают padding или jitter.
Однако они используют тот же последовательный writer: уже выполняющаяся
отправка большого IP-пакета, ожидание токенов или jitter могут их задержать.
Очень низкая скорость либо слишком большой jitter могут привести к idle timeout.

### Профили `upload` и `download`

| Поле | По умолчанию при пропуске | Диапазон и действие |
|---|---|---|
| `padding` | `false` | Добавлять криптографически случайные байты до выбранного целевого размера. Работает только в `profiled`. |
| `fragment` | `false` | Делить один IP-пакет на несколько собственных envelope-фрагментов. Это не IP fragmentation и не принудительная нарезка TCP. |
| `frame_min_bytes` | 1200; также при `0` | 64..16384, не больше max. Нижняя граница целевого DATA-фрейма, включая 4-байтный length prefix и 16-байтный envelope-заголовок. |
| `frame_max_bytes` | 1800; также при `0` | От min до 16384. Верхняя граница целевого размера; исключения при выключенном `fragment` описаны ниже. |
| `jitter_max_ms` | 0 | 0..100 миллисекунд. После каждого DATA-фрейма случайное целое ожидание 0..max включительно. При `0` дополнительного ожидания нет. |
| `small_packet_no_padding_bytes` | 0 | 0..MTU. `0`: исключение выключено. Если полный IP-пакет не больше порога, он отправляется обычным DATA без padding И fragmentation. Jitter при этом сохраняется. |

В новом шаблоне `init-server` порог малых пакетов явно равен 128 в обоих
направлениях. При отсутствии этого поля в существующем JSON порог равен 0.
Порог оценивается по полному IP-пакету, включая его IP-заголовок; это не
размер TCP payload и не специальное распознавание ACK, DNS или ICMP.

### Геометрия фреймов

- **Обычный DATA:** 4 байта длины + 1 байт типа + целый IP-пакет.
  Собственные накладные расходы 5 байт.
- **Envelope DATA:** 4 байта длины + 16 байт метаданных + фрагмент IP + padding.
  Собственные накладные расходы 20 байт на фрейм.
- **Выбор цели:** для каждого envelope-фрейма независимо выбирается целое
  число байт равномерно между min и max включительно. Это простая
  равномерная модель, не распределение, восстановленное из RDP-дампа.
- **`padding: true`, `fragment: false`:** IP остаётся целым. Если IP + 20
  больше выбранной цели, он не обрезается и фрейм может превысить
  `frame_max_bytes`. Это ожидаемое поведение, не ошибка MTU.
- **`fragment: true`, `padding: false`:** длина полезного фрагмента не больше
  target − 20; последний фрейм может быть меньше min.
- **Оба `true`:** каждый фрейм, включая последний, добивается padding до
  случайной цели. Целый IP-пакет собирается на принимающей стороне до TUN.
- **Оба `false`:** envelope не используется и min/max не задают размер DATA;
  один IP-пакет передаётся обычным сообщением. Jitter, если задан, применяется
  после такого сообщения.

Одновременно собирается только один IP-пакет на направление сеанса.
Длина, offset, идентификатор и флаги проверяются; IP ограничен MTU, envelope
ограничен 16384 байт с length prefix. Неправильная последовательность фрагментов
завершает сеанс. Ping/pong допустимы между фрагментами.

Таймаут сборки проверяется при чтении очередного фрейма, а не отдельным
таймером на каждый IP. Если новые данные совсем не приходят, соединение
ограничивается также общим idle timeout. Нельзя трактовать этот параметр
как точный read deadline системного сокета.

### Как jitter влияет на скорость

Jitter не является источником токенов и не компенсируется увеличением лимита.
Он добавляет ожидание после каждого DATA-фрейма, в том числе последнего
фрагмента пакета. Чем мельче фрагменты, тем больше ожиданий на тот же объём IP.

Например, при среднем фрейме 700 байт и среднем ожидании 5 мс только
этот механизм даёт ориентир 700 × 8 / 0,005 = 1,12 Мбит/с собственного
frame-потока, ещё без остальных накладных расходов. Фактическое ожидание
зависит от планировщика ОС и может быть больше запрошенного.

Начинайте с `jitter_max_ms: 0`. Для сравнения padding и fragmentation
не меняйте jitter одновременно: иначе трудно установить причину падения
скорости. Числовое сходство размеров не доказывает сходства с реальной
RDP-сессией, особенно при разных приложениях и RTT.

### Keepalive

В новом режиме ping отправляется после простоя исходящей передачи, а не
безусловно каждые 10 секунд поверх активного DATA. Ожидание выбирается
заново после отправки; ответом служит pong. Входящий односторонний поток
сам по себе не отменяет исходящие ping: это позволяет проверять обратное
направление при длительном одностороннем обмене.

Это собственные служебные сообщения нашего DVC, не поддельные графические
PDU или встроенный RDP keepalive. Их собственный размер 5 байт с prefix;
фактические внешние заголовки добавляет FreeRDP/TLS/TCP.

## Пресеты для контролируемого эксперимента

В `examples/` находятся JSON-объекты с полями для переноса в серверный
конфиг. Это не полные конфигурации и не отдельные файлы для `run -config`.
Заменяйте целиком старый блок `transport`, не создавая второй одноимённый
ключ, а `stats_interval_seconds` меняйте на верхнем уровне.

- **`transport-baseline.json`:** никаких модификаторов и встроенных лимитов,
  статистика каждые 10 секунд. Начальный контрольный замер.
- **`transport-padding-download.json`:** padding только download, без
  fragmentation/jitter, цель 1200..1800, малые IP до 128 байт исключены.
  Лимиты включены и берутся из существующих `total_*_bps`/`clients[]`.
- **`transport-fragmented.json`:** оба направления 400..900 байт,
  padding и fragmentation включены, jitter 0. Исключение до 128 байт.
  Это нагрузочный эксперимент со старой геометрией, не рекомендованный
  «RDP-видеопрофиль» и не результат подгонки по pcap.

Для каждого замера сохраняйте оба конфига, `POLICY` и финальные `STATS`,
направление теста, RTT, скорость напрямую и через туннель. Меняйте один
фактор за раз; отдельно сравнивайте upload и download, а не только speedtest.

## Статистика и интерпретация

После успешной v2-авторизации обе стороны печатают строку `POLICY` с
эффективными серверными настройками; UUID, ключ, nonce и содержимое IP
в ней отсутствуют. Это лучше, чем гадать, какие настройки применились.
Дополнительные локальные `total_*_bps` клиента не переписывают серверную
`POLICY`, поэтому их нужно проверять отдельно в клиентском JSON.

Записи `STATS` содержат JSON. Если соединение закрылось до авторизации,
такой статистики сеанса не будет. При штатном завершении после остановки
рабочих горутин выдаётся финальная запись; при принудительном kill,
падении процесса или отключении питания она не гарантирована.

| Поля | Смысл |
|---|---|
| `side`, `id` | `"server"`/`"client"` и метка; на сервере ID allowlist, на клиенте `"client"`. |
| `tx_direction` | Upload на клиенте, download на сервере. `rx` имеет обратное направление. |
| `final` | `true` у итоговой записи; иначе периодическая. |
| `elapsed_seconds` | Возраст измеряемого сеанса после установки профиля. |
| `interval_seconds` | Период для расчёта Mbps; у final весь сеанс, у периодической записи время после предыдущей. |
| `tx_ip_packets`, `tx_ip_bytes` | Полностью переданные нашему native IPC IP-пакеты и их полная IP-длина; не гарантия доставки удалённому TUN. Частично отправленный IP не включается как целый. |
| `rx_ip_packets`, `rx_ip_bytes` | Полные собранные входящие IP, после транспортного limiter, до проверки IP policy и записи TUN. |
| `rx_tun_packets`, `rx_tun_bytes` | IP, действительно успешно записанные в локальный TUN после policy. Разница с `rx_ip_*` требует проверки фильтрации/ошибки. |
| `tx_frames`, `rx_frames` | Собственные прикладные фреймы после авторизации, включая DATA/envelope и ping/pong. Не TCP-пакеты и не RDP PDU. |
| `tx_frame_bytes`, `rx_frame_bytes` | Сумма длины этих фреймов с 4-байтным length prefix. Не внешний wire traffic. |
| `tx_padding_bytes`, `rx_padding_bytes` | Только байты набивки. |
| `tx_payload_bytes`, `rx_payload_bytes` | IP-байты по фрагментам, без padding и наших заголовков. Могут включать часть ещё не завершённого IP. |
| `tx_header_bytes`, `rx_header_bytes` | Собственные заголовки: обычный DATA/control 5 байт, envelope 20 байт с prefix. |
| `tx_control_frames`, `rx_control_frames` | Количество ping/pong. |
| `tx_limiter_wait_ms`, `rx_limiter_wait_ms` | Накопленное время вызовов включённых ненулевых limiter, включая ожидание и небольшой программный overhead. Не длительность всех сетевых задержек. |
| `tx_jitter_wait_ms` | Накопленное фактическое ожидание jitter, с влиянием планировщика ОС. |
| `tx_pipe_write_ms` | Накопленное время записи Go → native pipe. Может показывать обратное давление, но не является измерением времени TLS send или RTT. |
| `tx_ip_mbps`, `rx_ip_mbps` | IP-скорость: периодическая за интервал, final средняя за весь сеанс. Десятичные Мбит/с. |
| `tx_frame_mbps`, `rx_frame_mbps` | Та же формула по собственным frame-байтам; padding включён. Не физическая скорость интерфейса. |
| `queue_depth` | Текущее количество сообщений исходящей Go-очереди. Не количество байт и не native/OS TCP backlog. |
| `queue_drops` | Накопленные отбрасывания новых IP из-за переполнения серверной Go-очереди; на клиенте 0, поскольку он использует backpressure. |
| `filtered_packets` | Накопленная фильтрация IP policy, включая неподдерживаемые multicast/broadcast назначения. Не все возможные причины сетевых потерь. |

Все счётчики количества, байт и времени накопительные с начала сеанса.
Снимки atomics не транзакционные, поэтому при активном обмене соседние
поля могут относиться к немного разным моментам. Для исправного завершённого
потока `frame_bytes` раскладывается на `payload_bytes + header_bytes +
padding_bytes`; у аварийно оборванного или некорректного входящего фрейма
сходимость не гарантируется.

Большие `tx_limiter_wait_ms` указывают на влияние лимитов; большие
`tx_jitter_wait_ms` показывают цену искусственных пауз. Рост
`queue_drops` означает переполнение серверной очереди, а не доказанный
packet loss внешнего TCP. Для реальных размеров/таймингов на проводе нужен pcap.

## Версии и миграция

- **Новый клиент → новый сервер:** UUID-авторизация v2; серверный профиль
  и лимиты включены в HMAC-подтверждение вместе с nonce, IPv4 и MTU.
  Подмена профиля в канале без корректного HMAC отклоняется.
- **Клиент 0.1.0–0.1.2 → сервер 0.1.3:** допускается только если серверный
  JSON не задаёт `transport` и `stats_interval_seconds`. Остаётся старый
  формат, прежние лимиты и ping раз в 10 секунд, без новых `POLICY`/`STATS`.
- **Новый клиент → старый сервер:** не поддерживается; автоматического
  downgrade до старого auth нет. Сначала обновите сервер, затем клиентов.
- **Явные новые настройки:** требуют клиента 0.1.3+. Генератор `init-server`
  0.1.3 сразу записывает новые блоки, поэтому его шаблон не предназначен
  для старых клиентов.
- **Native-компоненты:** прежние 0.1.0/FreeRDP 3.28.0, совместимы с новой
  Go-обвязкой. Не смешивайте DLL/SO с произвольной системной версией FreeRDP.

Это отдельный проект FreeRDPTun, не RDPTun 0.4.0. Поля старого проекта
`shaping`, `state_dir`, `max_handshakes` и старый блок `transport` нельзя
переносить механически: неизвестные имена отклоняются, смысл baseline
и размеры заголовков здесь другие.

## Что не регулируется JSON

В 0.1.3 нет настройки TLS record size, MSS, TCP segmentation, ClientHello
fingerprint, RDP graphics codec, RTTV-based адаптации или весов справедливого
распределения скорости. Подстройка `transport` не меняет тип RDP security
и не включает UDP: этот комплект использует TCP.

Нативная очередь и event loop FreeRDP, доверие к сертификату, UUID/HMAC и
IP-ownership не отключаются параметрами padding/shaping. Полноценного
CredSSP/NTLM/Kerberos-сервера, IPv6 туннеля, автоматического reconnect,
GUI/iOS и горячего reload нет.

## Команды обслуживания

Эти команды предназначены для запуска пользователем. Для обновления
достаточно заменить бинарники, выполнить `check` и перезапустить
соответствующие процессы; новый state создавать не нужно.

| Команда | Назначение |
|---|---|
| `freerdptun version` | Версия главной Go-программы, не версия native-моста. |
| `freerdptun check -config PATH` | Только загрузка/валидация JSON. Путь по умолчанию `server.json`. |
| `freerdptun run -config PATH` | Создать TUN, при необходимости настроить его и запустить выбранный режим. |
| `freerdptun new-uuid` | Сгенерировать новый секрет UUIDv4 для новой записи клиента. |
| `freerdptun fingerprint -cert PATH` | SHA-256 DER leaf из PEM; `-cert` по умолчанию `server.crt`. |
| `freerdptun init-server -dir NEW_DIR -server HOST:3389` | Создать новый каталог, UUID, RSA-ключ/сертификат и две конфигурации. По умолчанию `-dir ./state`, `-server SERVER_IP:3389`; не использовать для обновления существующего state. |
| `freerdptun selftest -config PATH` | В вашей песочнице: реальный native FreeRDP/DVC echo на loopback без TUN; не проверяет новые транспортные модификаторы. |

На Windows используйте `.\freerdptun.exe` вместо `freerdptun`.
Для `run` нужны административные права и native-комплект. TLS-пин и
UUID нового клиента нужно передавать ему доверенным способом.
