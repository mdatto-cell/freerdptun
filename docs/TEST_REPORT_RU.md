# FreeRDPTun 0.1.0: отчёт о проверках

Это исторический отчёт только о версии 0.1.0. Он не подтверждает работу
версий 0.1.1–0.1.3: по просьбе пользователя для них не запускались тесты,
`selftest` или реальные соединения. Синтетический unicast в прежних тестах
не выявил ошибку реакции на неподдерживаемый фоновый трафик; сведения
об изменениях находятся в `docs/UPDATE_0.1.1_RU.md`, `docs/UPDATE_0.1.2_RU.md`
и `docs/UPDATE_0.1.3_RU.md`.

Проверки выполнены 4 ноября 2026 года. Это новый экспериментальный проект
FreeRDP–FreeRDP, не обновление прежнего RDPTun и не результат испытаний
в вашей сети.

## Состав сборки

- **Приложение:** Go 1.26.8, `CGO_ENABLED=0`, Linux amd64 и Windows amd64.
- **Нативный транспорт:** FreeRDP/WinPR 3.28.0, commit
  `5370fb26fbf034ecd11d3026b6ad639b5fff493f`.
- **Linux:** нативные файлы собраны внутри Ubuntu 22.04 x64, GCC 11,
  системные OpenSSL 3, zlib и zstd.
- **Windows:** кросс-сборка MinGW-w64 GCC 13-win32, статический OpenSSL 3.5.9,
  оригинальная подписанная Wintun 0.14.1.

Точные ссылки, лицензии и хеши исходных архивов сторонних компонентов
находятся в `THIRD_PARTY.md`. Собственные тестовые сертификаты и секретные
UUID не включены в поставку; `init-server` создаёт новые непосредственно
на вашей машине.

## Автоматические проверки Go

Выполнены `go vet ./...` и `GOOS=windows GOARCH=amd64 go vet ./...` без замечаний.
Полный набор запускался с `go test -race ./... -count=1`; гонок Go-памяти
и провалов тестов не обнаружено.

Четырнадцать модульных тестов проверяют:

- **Авторизацию:** успешный обмен, отказ неизвестному UUID и неверному IPv4,
  производный публичный ID вместо секрета, разделение ролей HMAC и свежесть nonce.
- **Фрейминг:** обмен сообщениями, неверные длины и короткие записи.
- **Валидацию:** IPv4-пакеты, UUID, конфигурацию и дубликаты клиентов.
- **Сеансы и очереди:** отказ дубликату активного клиента и ограниченную очередь.
- **Лимиты:** отмену ожидания по контексту и ограничение устойчивого потока
  с учётом стартового запаса токенов.

Дополнительно выполнены два десятисекундных fuzz-запуска, каждый с двумя
работниками. Последний запуск `FuzzFrameRead` обработал 459 792 входа,
`FuzzIPv4` обработал 519 785 входов; оба завершились успешно.

```bash
go test -race ./... -count=1
go vet ./...
GOOS=windows GOARCH=amd64 go vet ./...
go test ./internal/tunnel -run '^$' -fuzz FuzzFrameRead -fuzztime=10s -parallel=2
go test ./internal/tunnel -run '^$' -fuzz FuzzIPv4 -fuzztime=10s -parallel=2
```

Race detector проверяет Go-код, но не заменяет анализ гонок внутри нативных
библиотек. Fuzzing был коротким и не является исчерпывающим аудитом.

## Интеграционные проверки настоящего FreeRDP

Все три native-теста выполнены, а не пропущены. Они используют настоящий
TCP loopback, FreeRDP negotiation/TLS/activation/DRDYNVC и наш DVC, но заменяют
TUN интерфейсом в памяти, поэтому не требуют изменения сети.

- **`TestNativeTwoClients`:** два клиента одновременно авторизуются на одном
  сервере; IPv4-пакеты проходят в обе стороны к правильному клиенту,
  побайтовое содержимое сохраняется, процессы штатно завершаются.
- **`TestNativeSelfTest`:** challenge-response по UUID и проверка pin,
  затем echo сообщений длиной 1, 64, 1401, 17000 и 65535 байт.
  Проверяется в том числе передача сообщения крупнее одного IP-пакета.
- **`TestNativeRejectPin`:** неверный SHA-256 pin приводит к отказу подключения,
  без ожидания полного внешнего тайм-аута.

Для повторения сначала создайте новый временный state, затем выполните:

```bash
dist/linux-amd64/freerdptun init-server -dir /tmp/frdptun-new-test
RDPT_SERVER_CONFIG=/tmp/frdptun-new-test/server.json \
RDPT_BRIDGE="$PWD/dist/linux-amd64/rdpt-bridge" \
  go test -race ./internal/tunnel -run TestNative -v -count=1
```

Без переменной `RDPT_SERVER_CONFIG` эти три теста намеренно пропускаются.
Обычный успешный `go test` сам по себе не подтверждает работу нативного стека.

## Проверки комплектов

- **Ubuntu 22.04:** готовые Linux-файлы выполнили `selftest` внутри Ubuntu
  22.04 rootfs; все пять размеров echo прошли, как и авторизация с pin.
  Проверен запуск от root с понижением привилегий нативных процессов.
- **Linux ABI:** проверены ELF-зависимости и символы glibc; максимальная
  требуемая версия GLIBC для поставляемого нативного комплекта не выше 2.34.
  В Ubuntu 22.04 используется glibc 2.35.
- **Загрузка библиотек:** Linux-транспорт запускается с библиотеками
  из собственного `lib/` через `$ORIGIN/lib`, без глобального `LD_LIBRARY_PATH`.
  Для chroot без смонтированного `/proc` отдельно задавались абсолютный
  путь `bridge` и локальный `LD_LIBRARY_PATH` только на время этого теста.
- **Windows PE:** проверены импортируемые DLL и наличие необходимых
  несистемных зависимостей рядом с EXE; OpenSSL слинкован статически.
  Системные Windows DLL не включены в архив.
- **Wintun:** поставляемая DLL побайтово совпадает с оригинальной amd64 DLL
  официального комплекта, не модифицировалась и не обрабатывалась `strip`.
- **Сценарии и служба:** shell-сценарии прошли `bash -n`; пример systemd unit
  проверен анализатором. Работа службы в реальной установленной ОС не проверялась.
- **Архив:** целостность ZIP и суммы файлов `dist` проверены после упаковки
  и повторной распаковки.

## Что предстоит проверить у вас

- **Windows runtime:** фактический запуск EXE, создание Wintun, назначение IPv4,
  подключение к Ubuntu и завершение через `Ctrl+C`. В этой среде Windows
  не запускалась; успешная кросс-сборка этого не доказывает.
- **Настоящий TUN:** адреса, link up, ping, маршрутизация, firewall,
  forwarding, NAT и доступ к выбранным сетям.
- **Нагрузка:** пропускная способность, CPU/RAM, RTT, потери, несколько
  продолжительных сеансов, взаимодействие суммарных и индивидуальных лимитов.
- **Сеть и классификация:** дамп Wireshark и поведение конкретного DPI.
  Ни сходство с `mstsc`, ни неотличимость от видеосессии не заявляются.
- **Эксплуатация:** системная служба, переподключение после обрыва,
  восстановление ручных настроек интерфейса после перезапуска.

Рекомендуемый первый опыт: один Linux-клиент без смены default route,
проверка ping и короткого `iperf3`, затем Windows и второй UUID. Автоматического
reconnect в этой версии нет; после обрыва клиент нужно запустить снова.
