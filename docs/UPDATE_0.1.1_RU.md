# FreeRDPTun 0.1.1: исправление отключения Windows

Это историческая инструкция для 0.1.1. После её выпуска пользователь подтвердил
прохождение трафика. В 0.1.2 настройка адресов автоматизирована; для актуального
обновления используйте `docs/UPDATE_0.1.2_RU.md`, а не ручные команды ниже.

Обновление устанавливается поверх FreeRDPTun 0.1.0. Конфигурации, UUID,
certificate pin, серверный сертификат и ключ сохраняются; не запускайте
`init-server` повторно.

## Причина исправления

Серверный журнал пользователя подтвердил разрыв сеанса в проверке
`IPv4 source/destination ownership violation`. В версии 0.1.0 одна ветка
смешивала неподдерживаемое назначение IP-пакета и настоящую подмену адреса.
В обоих случаях сервер завершал весь сеанс.

Вероятный триггер при назначении IPv4 Windows-интерфейсу: фоновый multicast
либо broadcast с разрешённым исходным IP. Конкретный адрес вызвавшего разрыв
пакета в старом журнале не записан, поэтому он пока не установлен.
Исправление устраняет найденный дефект политики и расширяет диагностику,
но ещё не подтверждено повторным испытанием в сети пользователя.

## Что изменено

- **Сервер:** неподдерживаемый адрес назначения не завершает сеанс.
  Такой пакет отбрасывается до записи в TUN.
- **Клиент:** неподдерживаемые назначения фильтруются до отправки в DVC.
- **Broadcast:** учитывается не только `255.255.255.255`, но и broadcast
  настроенной подсети туннеля, например `10.77.0.255` для `/24`.
- **Защита источника:** пакет с исходным адресом, отличным от назначенного
  клиенту, по-прежнему завершает сеанс; проверка не отключена.
- **Журнал:** настоящие нарушения содержат `src`, `dst` и ожидаемый адрес.
  Первые три фильтрации содержат адреса и `session kept`; итоговый счётчик
  выводится при завершении сеанса.
- **Регрессионный код:** добавлены тесты политики и продолжения передачи
  unicast после неподдерживаемых пакетов, без их запуска в этой поставке.

Формат прикладного протокола не менялся. Новая Go-программа имеет версию
0.1.1, а `rdpt-bridge` и FreeRDP/DLL/SO остаются прежними.
Обновлённый сервер совместим с клиентом 0.1.0; для устранения описанного
серверного разрыва можно сначала заменить только серверную Go-программу.
Рекомендуется затем заменить и клиентскую.

## Содержимое пакета исправления

Пакет не является самостоятельным дистрибутивом. Он содержит:

- **`dist/linux-amd64/freerdptun`:** новая серверная/клиентская Go-программа.
- **`dist/windows-amd64/freerdptun.exe`:** новая клиентская Go-программа.
- **`source/`:** полный Go-код приложения и актуальные собственные документы
  для наложения на исходный проект 0.1.0.
- **`SHA256SUMS`:** контрольные суммы файлов пакета.

Нативные `rdpt-bridge`, библиотеки FreeRDP/WinPR и Wintun берутся из уже
установленного комплекта 0.1.0. Их заменять не требуется.

## Обновление Ubuntu-сервера

Распакуйте пакет и перейдите в каталог `freerdptun-0.1.1-hotfix`.
Проверьте суммы файлов, затем остановите службу, сохраните предыдущий
исполняемый файл и установите новый:

```bash
sha256sum -c SHA256SUMS

sudo systemctl stop freerdptun
sudo cp -an /opt/freerdptun/freerdptun /opt/freerdptun/freerdptun.before-0.1.1
sudo install -o root -g root -m 755 \
  dist/linux-amd64/freerdptun /opt/freerdptun/freerdptun

/opt/freerdptun/freerdptun version
sudo systemctl start freerdptun
```

Команда `version` должна показать `FreeRDPTun 0.1.1`. Файлы
`/etc/freerdptun/server.json`, сертификат и ключ оставьте без изменений.

После перезапуска интерфейс создаётся заново. Для вашей текущей адресации
вручную верните параметры, если имя/MTU в конфигурации не менялись:

```bash
sudo ip address replace 10.77.0.1/24 dev frdptun0
sudo ip link set dev frdptun0 mtu 1400 up
sudo journalctl -u freerdptun -f -o cat
```

Эти команды не меняют маршруты по умолчанию, NAT или DNS.
В журнале старого клиента при новом сервере могут появиться строки:

```text
filtered unsupported IPv4 destination: direction=received src=10.77.0.2 dst=224.0.0.22 count=1 (session kept)
```

Это пример формата, а не адрес пакета, уже установленный по вашему дампу.
Такая строка означает фильтрацию отдельного пакета, не отказ авторизации.

## Обновление Windows-клиента

Закройте клиент перед заменой EXE. Из распакованного пакета скопируйте
`dist\windows-amd64\freerdptun.exe` поверх `C:\FreeRDPTun\freerdptun.exe`;
остальные DLL, `rdpt-bridge.exe` и ваш `client.json` не изменяйте.

В PowerShell от администратора:

```powershell
cd C:\FreeRDPTun
.\freerdptun.exe version
.\freerdptun.exe run -config .\client.json
```

Во втором PowerShell после появления интерфейса снова назначьте адрес:

```powershell
New-NetIPAddress -InterfaceAlias "frdptun0" -AddressFamily IPv4 `
  -IPAddress 10.77.0.2 -PrefixLength 24 -PolicyStore ActiveStore

Set-NetIPInterface -InterfaceAlias "frdptun0" -AddressFamily IPv4 -NlMtuBytes 1400

Find-NetRoute -RemoteIPAddress 10.77.0.1
ping -n 4 10.77.0.1
```

Маршруты по умолчанию пока не меняйте. На сервере при необходимости
подтвердите прохождение ping именно по TUN:

```bash
sudo tcpdump -ni frdptun0 'icmp and host 10.77.0.2'
```

Если сеанс всё равно завершается, пришлите серверную строку `disconnected`
с новыми полями `src`, `dst`, `expected_source` либо `expected_destination`
и соответствующий клиентский журнал. Не присылайте UUID и закрытые ключи.

## Исходники и ограничения проверки

Чтобы обновить исходный проект, скопируйте содержимое `source/` поверх
каталога проекта 0.1.0 с сохранением относительных путей. Зависимости
`third_party/FreeRDP`, нативный код и сборочные сценарии не изменены.

Для 0.1.1 выполнены компиляция Linux/Windows Go-программ и статический анализ.
По просьбе пользователя не запускались модульные/интеграционные тесты,
`selftest`, сервер, клиент или настоящие TUN-соединения.
Предыдущий отчёт о проверках относится только к 0.1.0.
